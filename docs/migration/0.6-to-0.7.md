# Migrating from 0.6 to 0.7

0.7.0 is released and contains source-breaking public API changes from 0.6.
The protocol remains version 2, so this FD ownership change does not alter the
wire format.

## Beginner response helper

The aggregate response form remains source-compatible:

```cpp
return easy_uds::Response{easy_uds::status_ok, body};
```

0.7 also provides the optional equivalent `easy_uds::Response::ok(body)` for
the common successful reply. It is an inline, layout-neutral convenience; it
does not replace explicit status values or change protocol framing.

## File descriptor ownership

The 0.6 API represented both borrowed and owned descriptors as raw `int`
values. In 0.7, the caller passes a `BorrowedFd` and the server receives an
`OwnedFd`:

```cpp
// 0.6
client.request_fd("read", fd);
server.on("/read", [](const easy_uds::Request& request) {
    if (request.fd < 0) { /* no descriptor */ }
    consume(request.fd);
    const int retained = ::dup(request.fd);
    return easy_uds::Response{200, {}};
});

// 0.7
client.request_fd("read", easy_uds::borrow_fd(fd));
server.on("/read", [](const easy_uds::Request& request) {
    if (!request.fd.valid()) { /* no descriptor */ }
    consume(request.fd.get());
    easy_uds::OwnedFd retained = request.fd.duplicate();
    return easy_uds::Response{200, {}};
});
```

The client still owns and closes its original descriptor. `Request` now owns
the received duplicate and closes it automatically. Because `OwnedFd` is
move-only, `Request` is also move-only; handlers continue to receive it as
`const Request&`, so ordinary handler signatures do not change.

This change removes ambiguous double ownership and makes exceptional,
timed-out, rejected, and queued request cleanup follow the same RAII path. See
[the FD passing reference](../api/fd-passing.md) for full lifetime, error, and
thread-safety semantics.

## Operational errors

0.6 exposed socket errors directly as `std::system_error` and used
`std::runtime_error`, `std::length_error`, or sticky `std::logic_error` for
some protocol and Session failures. 0.7 reports operational failures as one
`easy_uds::Error` with a stable `ErrorCode` and an optional original OS code:

```cpp
// 0.6
try {
    client.request("/read");
} catch (const std::system_error& error) {
    if (error.code().value() == ETIMEDOUT) {
        handle_timeout();
    }
}

// 0.7
try {
    client.request("/read");
} catch (const easy_uds::Error& error) {
    if (error.code() == easy_uds::ErrorCode::timeout) {
        handle_timeout();
    }
    if (error.system_code() ==
        std::error_code(ETIMEDOUT, std::generic_category())) {
        record_linux_timeout();
    }
}
```

`Error` still derives from `std::system_error`, so a broad existing catch keeps
working. The important source change is that inherited `code()` now uses the
`easy_uds` category; code that inspected `errno` through `code()` must use
`system_code()`.

Other changes:

- invalid response framing and correlation IDs now report `protocol`;
- peer responses exceeding receive limits now report `too_large`, while
  oversized locally supplied input remains `std::length_error`;
- a permanently broken Session rejects later calls with `closed` rather than
  `std::logic_error`;
- invalid local arguments and invalid object lifecycle continue to use
  `std::invalid_argument` and `std::logic_error`.

No error triggers implicit reconnect or replay. See the
[error reference](../api/errors.md) for classification and retry semantics.

## Session state inspection

0.6 had no public way to distinguish a currently usable Session, a sticky
broken connection, and a moved-from object without attempting a request. 0.7
adds an explicit snapshot without changing request or wire behavior:

```cpp
if (session.status() == easy_uds::SessionStatus::broken) {
    session = client.session(); // only when the application decides retry is safe
}
```

`valid()` is shorthand for an `active` status. An active snapshot is not a
liveness probe or a guarantee that the next request succeeds; applications
must still handle `Error`. Neither API performs I/O, reconnects, nor replays a
request. See the [Session state reference](../api/session.md) for transitions,
thread safety, and move semantics.

## Header organization

The 0.6 umbrella remains valid and still exposes the complete API:

```cpp
#include <easy_uds/easy_uds.hpp>
```

0.7 additionally provides self-contained feature headers such as
`client.hpp`, `session.hpp`, `server.hpp`, `request.hpp`, `response.hpp`,
`stream.hpp`, and `options.hpp`. Switching to them is optional and does not
change object layout, symbols, or protocol v2. Installed applications must not
include files below `src/`; those implementation paths were reorganized and
are intentionally outside the public compatibility contract. See the
[public header and source map](../api/headers.md).

## Optional Simple API facade

0.7 promotes the audited beginner facade as an optional, fixed-request API. It
is a wrapper around the existing Core `Server`/`Client`; it does not create a
second reactor, transport, registry, or retry policy:

```cpp
#include <easy_uds/simple.hpp>

easy_uds::simple::Server server("/tmp/echo.sock");
server.on("/ping") = "pong";
server.on("/echo") = [](std::string_view body) { return std::string(body); };
server.run();

easy_uds::simple::Client client("/tmp/echo.sock");
const std::string body = client.request("/echo", "hello");
```

The route proxy is intentionally temporary-only: registration must be written
as `server.on("/ping") = handler`, while retaining the proxy in a variable is
rejected at compile time. Supported handler inputs are exactly `()` and
`(std::string_view)`; supported results are string-like values (`std::string`,
`std::string_view`, and non-null C strings). A null C string fails
deterministically with a 500 response and the message
`easy-uds simple handler returned a null C string`.

Simple transport/protocol/timeout/closed failures continue to use Core
`easy_uds::Error`. A non-200 application response throws
`easy_uds::simple::ResponseError`, preserving both `status()` and `body()`.
Duplicate routes retain Core semantics and throw `std::runtime_error`; they do
not silently replace an earlier registration. Advanced applications can use
`server.core()`/`client.core()` to share the same lifecycle and registry with
the full Core API.

The facade deliberately does not add Simple `Session`, streaming, stats,
context, options, retries, reconnects, or typed RPC in 0.7. Keep those use
cases on the Core API until they have separate contracts. See the
[Simple API guide](../simple-api/getting-started.md) and the promotion audit
for the complete boundary.

## Request context (additive)

The existing handler form remains source-compatible:

```cpp
server.on("/ping", [](const easy_uds::Request&) {
    return easy_uds::Response{200, "pong"};
});
```

0.7 adds an explicit advanced form rather than changing that callback:

```cpp
server.on(
    "/work",
    easy_uds::RouteOptions{
        [](const easy_uds::Request& request,
           const easy_uds::RequestContext& context) {
            if (context.stop_requested()) {
                return easy_uds::Response{408, "expired"};
            }
            return easy_uds::Response{200, request.body};
        }});
```

`RequestContext` is valid only while the callback is running and cannot be
copied or moved. Its connection state is an observation, not a liveness probe,
and cancellation is cooperative. See the
[request-context reference](../api/request-context.md).

## Runtime statistics (additive)

`Server::stats()` and `Session::stats()` are new observer APIs. Existing code
does not need to enable or call them. Server gauges reuse correctness and
backpressure accounting; cumulative server counters remain disabled unless
explicitly requested:

```cpp
easy_uds::ServerOptions options;
options.stats = easy_uds::StatsMode::basic;

easy_uds::ClientOptions client_options;
client_options.stats = easy_uds::StatsMode::basic; // Session counters
```

The disabled default adds no counter atomic RMW to fixed RPC. Enabled Session
outcomes are accumulated under the existing in-flight shard locks. Snapshots are
thread-safe and best-effort rather than transactionally consistent across all
fields. See the [stats reference](../api/stats.md).

## Serialized domains and queue policies (additive)

Existing `on_serialized(route, handler)` code keeps the 0.6 behavior: every
such route and `enqueue_maintenance()` shares one default FIFO domain. Advanced
scheduling is opt-in and does not change plain `on()`:

```cpp
server.on(
    "/velocity/set",
    easy_uds::RouteOptions{[](const easy_uds::Request& request) {
        return set_velocity(request.body);
    }}.serialize_in("drivetrain",
                    easy_uds::QueuePolicy::latest_wins));
```

`RouteOptions` now accepts simple handlers as well as contextual handlers.
Named domains may execute concurrently, bounded by
`ServerOptions::max_concurrent_serialized_domains` (`0` uses `worker_threads`).
`latest_wins` supersedes queued requests with the same concrete route and
domain; `reject_if_busy` rejects when the domain is executing or queued. Both
return `status_conflict` (409) as a normal response, never reconnect or retry,
and never interrupt a running handler. See the
[serialized scheduling reference](../api/route-options-design.md).
